# M4 — AppHost 插件系统与 headless UiHost

## 一句话总结

M4 把 AppHost 从“发送静态测试帧的网络端点”推进为“可以加载业务 `.so` 插件并运行 GKC UI 插件代码的服务端宿主”。AppHost 不创建真实窗口、不运行 GKC 的 Wayland/Win32 GUI host，而是自己实现一套 headless/fake `IUiHost` 函数表，让插件仍然可以用正常的 GKC `ToplevelImpl<T>` / `GuiHelper::Loop()` / `Show()` / `Damage()` 写业务 UI；每次插件 `DoDraw()` 完成后，AppHost 立即按 `rcPaint` 打包 `PIXEL_DATA` 发回 Gateway。

---

## 在整个项目中的位置

```
M1 (协议层) ✅ → M2 (IoPool + MessageHandler) ✅
                         ↓
                 M3 (Gateway 路由 + AppHost 进程生命周期) ✅
                         ↓
                 M4 (AppHost 插件系统 + headless UiHost) ✅ ← 当前完成
                         ↓
                 M5 (INPUT_EVENT 注入 + PostWork 主线程模型)
                         ↓
                 M6 (Client 插件系统 + 真实 GKC GUI host)
```

M4 是**服务端 UI 插件 milestone**。它完成的是服务端这一半：Gateway 可以启动 AppHost，AppHost 可以反连 Gateway、加载业务 `.so`、把插件绘制结果转换成协议像素包。Client 端真实窗口显示和输入闭环仍属于 M5/M6。

## 核心设计：AppHost 不跑真实 GKC GUI host

M4 最容易混淆的一点是：**插件仍然使用 GKC GUI wrapper，但 AppHost 不使用 GKC 的真实 GUI host 实现。**

两者区别如下：

| 位置 | 使用什么 | 不使用什么 |
|------|----------|------------|
| AppHost 宿主进程 | 自己实现的 `ui_host_impl`，即一张 `IUiHost` / `IUiWindow` / `IUiToplevel` C-style function table | GKC 真实 Wayland/Win32 UI host、真实窗口、真实 compositor、真实 GUI event loop |
| 插件 `.so` | GKC 插件侧 wrapper：`ToplevelImpl<T>`、`GuiHelper::Loop()`、`Show()`、`Damage()`、`_SA_UIMain` shim | 插件不直接知道 AppHost 的 C++ 类名 |
| Client 侧未来 M6 | 预计使用 GKC 真实 GUI host 显示远端像素 | 不属于 M4 范围 |

所以 M4 的 AppHost 是“不对称”的：

```
AppHost side:
  fake/headless IUiHost implemented by this project

Plugin business code:
  normal GKC GUI-style code

Client side:
  real GUI display comes later
```

插件代码看起来像普通 GKC GUI 程序：

```cpp
DemoWindow win;
win.Create(true, 32, 16);
win.Show(true);
win.Damage(small);
return GuiHelper::Loop();
```

但这些 wrapper 最终不会进入 GKC 真实窗口系统，而是通过注入的 `GKC::g_ui_host` 跳回 AppHost 的 fake `ui_host_impl`。

## `.so` Load 的作用

`.so` 是**已经编译好的业务应用模块**，不是接口描述文件。以 `plugins/demo_app/libdemo_app.so` 为例，它包含：

1. 插件业务代码：`DemoWindow::DoDraw()`、`GKC::ProgramEntryPoint::GuiMain()`。
2. 插件本地的 `GKC::g_ui_host` 全局变量。
3. GKC SA shim 导出的 C ABI 入口：`extern "C" int _SA_UIMain(...)`。
4. GKC wrapper 代码需要的插件侧 glue：`GkcDef.cpp`、`GkcSAMain.cpp`、`GkcGui.cpp`。

AppHost 在编译时不知道会加载哪个插件，也不知道插件里的 C++ 类名。因此双方约定所有插件都必须导出同一个 C ABI 符号：

```text
_SA_UIMain
```

当前 loader 的实际流程：

```text
PluginLoader::open(plugin_path)
  -> dlopen(plugin_path, RTLD_NOW | RTLD_LOCAL)
      Linux dynamic loader 把 .so 的代码、静态数据、符号表映射进 AppHost 进程

  -> dlsym(handle, "_SA_UIMain")
      在 .so 的符号表里找统一入口函数地址

  -> entry_ = reinterpret_cast<EntryFn>(sym)
      保存为可调用的函数指针

PluginLoader::run(lcHost)
  -> entry_(lcHost, empty_args)
      从 AppHost 代码跳进插件 .so 里的机器码
```

如果找不到 `_SA_UIMain`：

```text
dlsym() returns error
  -> PluginLoader::open() returns false
  -> AppHost::Impl::run() closes socket and returns -3
  -> apphost_bin exits non-zero
  -> Gateway monitor / socket close path treats AppHost startup as failed
```

找到以后为什么能执行插件代码：因为 `dlsym()` 返回的是 `.so` 里 `_SA_UIMain` 函数的内存地址。AppHost 把这个地址 cast 成函数指针后调用，CPU 就会跳到插件 `.so` 的代码段执行。

## `_SA_UIMain` 的作用

`_SA_UIMain` 是 AppHost 和任意插件之间的统一启动入口。它由插件 include 的 GKC `GkcGui.cpp` 提供，核心逻辑是：

```cpp
SA_FUNCTION_C int _SA_UIMain(
    const GKC::LcInterface<GKC::IUiHost>& lcHost,
    const GKC::ConstArray<GKC::ConstStringS>& args) SA_NOEXCEPT
{
    GKC::g_ui_host = lcHost;
    return program_entry_point::GuiMain(args);
}
```

它做两件事：

1. **注入 host 能力**：把 AppHost 传进来的 `lcHost` 保存到插件本地 `GKC::g_ui_host`。
2. **进入业务逻辑**：调用插件实现的 `ProgramEntryPoint::GuiMain(args)`。

因此调用关系是：

```text
AppHost
  -> plugin_.run(ui_host_.make_interface())
    -> _SA_UIMain(lcHost, args)
      -> plugin-local GKC::g_ui_host = lcHost
      -> GKC::ProgramEntryPoint::GuiMain(args)
        -> DemoWindow win
        -> win.Create(...)
        -> win.Show(true)
        -> win.Damage(...)
        -> GuiHelper::Loop()
```

## `LcInterface<IUiHost>` 如何连接插件和 AppHost

`LcInterface<IUiHost>` 可以理解为一对值：

```text
context pointer + function table pointer
```

在 AppHost 里，`UiHostImpl::make_interface()` 构造的是：

```text
context = this                       // AppHost 内的 UiHostImpl 实例
funcs   = &kHostTable                // AppHost 自己实现的 IUiHost 函数表
```

当前代码等价于：

```cpp
GKC::LcInterface<IUiHost> UiHostImpl::make_interface() {
    return GKC::LcInterface<IUiHost>(
        this,
        GKC::RefPtr<IUiHost>(&kHostTable)
    );
}
```

`kHostTable` 是 AppHost 的 fake host 函数表：

```cpp
const IUiHost kHostTable = {
    &on_host_loop,
    &on_host_quit,
    &on_host_post_work,
    &on_host_add_timer,
    &on_host_remove_timer,
    &on_host_create_toplevel,
    &on_host_create_dialog,
    &on_host_create_popup,
    &on_host_destroy,
};
```

插件的 `_SA_UIMain` 执行后：

```text
plugin-local GKC::g_ui_host
  = {
      context: AppHost UiHostImpl*,
      funcs:   AppHost kHostTable*
    }
```

之后插件调用 GKC wrapper 时，就会通过这对值回调 AppHost。

### 示例：`win.Create()`

```text
Plugin code:
  win.Create(true, 32, 16)

GKC wrapper:
  GKC::_Toplevel::Create()
    -> g_ui_host.GetFunc()->CreateToplevel(
           g_ui_host.GetContext(), true, 32, 16, &m_pToplevel)

Injected function table:
  kHostTable.CreateToplevel(context, ...)

AppHost implementation:
  on_host_create_toplevel(static_cast<UiHostImpl*>(context), ...)
    -> create WindowRuntime
    -> allocate std::vector<uint32_t> pixels
    -> return kToplevelTable
```

### 示例：`win.Show(true)`

```text
Plugin code:
  win.Show(true)

GKC wrapper:
  _WindowImpl<T>::Show()
    -> SetMessageHandler(id, UiMessageHandler{&Process}, this)
    -> Show(id, true)

AppHost implementation:
  on_window_set_message_handler(...)
    -> store plugin handler and plugin object pointer

  on_window_show(...)
    -> dispatch_draw_and_send(full window)
      -> handler.Process(..., UI_MESSAGE_DRAW, &UiMessageDraw)
        -> GKC::_WindowImpl<T>::Process()
          -> DemoWindow::DoDraw(pDraw)
      -> pack_pixel_data_rect(...)
      -> send PIXEL_DATA
```

这个链路体现了 M4 的双向调用：

```text
AppHost -> Plugin:
  call _SA_UIMain()
  call ProgramEntryPoint::GuiMain()
  dispatch UI_MESSAGE_DRAW into DemoWindow::DoDraw()

Plugin -> AppHost:
  win.Create()
  win.Show()
  win.Damage()
  GuiHelper::Loop()
  all call through g_ui_host into ui_host_impl
```

## headless UiHost 的窗口模型

`UiHostImpl::State` 维护 AppHost fake UI 的运行状态。M4 只支持一个 toplevel window：

```text
UiHostImpl::State
├── window: unique_ptr<WindowRuntime>
├── mtx / cv / quit_flag
├── post_queue
├── sink
└── frame_seq

WindowRuntime
├── host: UiHostImpl*
├── width / height
├── pixels: vector<uint32_t>       // GKC color_quad backing buffer
├── handler: UiMessageHandler      // plugin message handler
├── handler_ctx: void*             // plugin window object pointer
└── destroyed
```

`WindowRuntime::pixels` 是整窗 backing store。插件 `DoDraw()` 收到的 `pDraw->pBuffer` 指向这个 buffer，而不是一个真实窗口 surface。

`IUiToplevel` / `IUiWindow` 函数表由 `kToplevelTable` 提供：

```text
kToplevelTable.base.GetSize          -> on_window_get_size
kToplevelTable.base.Show             -> on_window_show
kToplevelTable.base.SetMessageHandler-> on_window_set_message_handler
kToplevelTable.base.SetClose         -> on_window_set_close
kToplevelTable.base.Damage           -> on_window_damage
```

M4 支持：

| 操作 | 行为 |
|------|------|
| `CreateToplevel` | 创建唯一 `WindowRuntime`，分配 `width * height` 个 `color_quad` |
| `Show(true)` | 同步派发整窗 `UI_MESSAGE_DRAW`，`rcPaint = {0,0,w,h}` |
| `Damage(rect)` | 裁剪 rect 到窗口范围，同步派发局部 `UI_MESSAGE_DRAW` |
| `Destroy` | 删除当前 `WindowRuntime` |
| `CreateDialogBox` / `CreatePopup` | M4 不支持，返回 0 |
| `AddTimer` | M4 stub，返回 0 |

## PIXEL_DATA 打包路径

M4 不做逐帧像素比对，也不保留旧 `PixelBuffer`。脏矩形直接来自 fake host 对 `Show(true)` / `Damage(rect)` 的派发。

完整路径：

```text
Plugin Show(true) or Damage(rect)
  -> on_window_show / on_window_damage
  -> dispatch_draw_and_send(w, left, top, right, bottom)
    -> build UiMessageDraw:
         pBuffer = WindowRuntime::pixels.data()
         iWidth / iHeight = window size
         rcPaint = requested dirty rect
    -> plugin handler.Process(..., UI_MESSAGE_DRAW, &msg)
      -> DemoWindow::DoDraw(pDraw)
        -> write color_quad pixels into pDraw->pBuffer
    -> pack_pixel_data_rect(pixels, stride, rect, frame_seq)
    -> pixel sink
    -> AppHost::send_pixel_data(body)
    -> protocol Header + body over TCP socket to Gateway
```

`pack_pixel_data_rect()` 做三件事：

1. 按 `[left,right) x [top,bottom)` 从整窗 `color_quad` buffer 裁出矩形。
2. 把 GKC `color_quad` 的内存语义转换成协议 wire 字节序。
3. 拼出完整 `PIXEL_DATA` Body：

```text
[frameSeq:4]
[rectLeft:4]
[rectTop:4]
[rectRight:4]
[rectBottom:4]
[dataLen:4]
[pixelData:dataLen]
```

字节序重点：

```text
GKC color_quad value:
  bit31..0 = A R G B

On little-endian Linux memory:
  bytes = B, G, R, A

Protocol wire pixelData:
  bytes = A, R, G, B
```

当前实现通过逐像素写 big-endian `uint32_t` 达到 `[A,R,G,B]` wire 顺序。

`capture_rect()` 仍保留，但它是 M2 遗留的“纯字节裁剪”工具，不做颜色通道重排；M4 主路径使用 `pack_pixel_data_rect()`。

## AppHost 运行时生命周期

AppHost 当前使用一个主动连接 Gateway 的 TCP socket，加一个 reader thread 处理控制消息。M4 的主路径如下：

```text
apphost_bin main()
  -> parse argv:
       --gateway-host
       --gateway-port
       --session-id
       --plugin
       --width
       --height

  -> AppHost::run(cfg)
    -> connect_to_gateway(cfg.gateway_host, cfg.gateway_port)
    -> send APPHOST_READY(session_id)
    -> register handlers:
         HEARTBEAT     -> echo HEARTBEAT
         CLOSE_SESSION -> ui_host_.request_quit()
         INPUT_EVENT   -> ignored in M4
    -> ui_host_.set_pixel_data_sink(...)
    -> plugin_.open(cfg.plugin_path)
    -> start reader_loop thread
    -> plugin_.run(ui_host_.make_interface())
      -> blocks until plugin GuiHelper::Loop() returns
    -> shutdown socket
    -> join reader thread
    -> return plugin exit code
```

`CLOSE_SESSION` 的退出路径：

```text
Gateway -> AppHost: CLOSE_SESSION
  -> reader_loop recv()
  -> MessageHandler feed()
  -> CLOSE_SESSION handler
  -> ui_host_.request_quit()
  -> on_host_quit()
     set quit_flag = true
     cv.notify_all()
  -> on_host_loop() wakes and returns
  -> GuiHelper::Loop() returns
  -> GuiMain returns
  -> _SA_UIMain returns
  -> plugin_.run() returns
  -> AppHost cleanup
```

## PostWork 在 M4 中的含义

M4 已经实现了 `PostWork` 队列，但还没有用它注入 `INPUT_EVENT`。它的作用是为 M5 留出线程切换模型，并兼容插件或 GKC wrapper 自己调用 `WorkImpl<T>::PostWork()`。

当前结构：

```cpp
struct PostedWork {
    WorkProc work;
    void*    data;
};

std::deque<PostedWork> post_queue;
```

可以理解为：

```text
PostedWork = function pointer + argument
```

执行路径：

```text
Any thread:
  on_host_post_work(ctx, work, data)
    -> post_queue.push_back({work, data})
    -> cv.notify_all()

Plugin main thread:
  on_host_loop(ctx)
    -> wait until quit_flag or post_queue non-empty
    -> pop PostedWork in FIFO order
    -> work.Exec(data)
```

未来 M5 的真实用途：

```text
Client mouse/keyboard
  -> Gateway
  -> AppHost reader/network thread receives INPUT_EVENT
  -> cannot safely call plugin DoMouse/DoKeyboard directly on reader thread
  -> package input as PostedWork
  -> PostWork into ui_host_impl
  -> plugin main thread drains queue inside GuiHelper::Loop()
  -> dispatch UI_MESSAGE_MOUSE / UI_MESSAGE_KEYBOARD to plugin handler
```

因此 `post_queue` 是 AppHost fake UIHost 的简化 UI event queue：它把跨线程事件安全地切回插件主线程。

## Demo 插件行为

`plugins/demo_app/demo_app.cpp` 是 M4 的验证插件，固定窗口大小为 `32 x 16`。当前 `--width/--height` 已由 Gateway/AppHost CLI 传递并解析，但 M4 的 `PluginLoader::run()` 还没有把 argv 转发给插件；demo 插件实际窗口尺寸由 `GuiMain()` 内的 `win.Create(true, 32, 16)` 决定。

插件绘制规则：

```text
Full window:
  blue background

Small rect:
  left=8, top=4, right=16, bottom=12
  first DoDraw from Show(true): red block
  second DoDraw from Damage(small): green block
```

`DemoWindow::DoDraw()` 当前使用 `damage_count_` 区分帧次：

```text
damage_count_ == 1:
  first full-frame DRAW from Show(true)
  -> small rect is RED

damage_count_ >= 2:
  dirty-rect DRAW from Damage(small)
  -> small rect is GREEN
```

这个变化让测试可以证明第二包 dirty-rect `PIXEL_DATA` 不是简单重复首帧小矩形内容，而是携带了插件在后续 `DoDraw()` 中写入的新像素。

插件生命周期：

```text
GuiMain()
  -> assert g_ui_host.GetFunc() is not null
  -> DemoWindow win
  -> win.Create(true, 32, 16)
  -> win.Show(true)
       AppHost sends full-frame PIXEL_DATA:
         full window blue, small rect red
  -> win.Damage({8,4,16,12})
       AppHost sends dirty-rect PIXEL_DATA:
         small rect green
  -> GuiHelper::Loop()
       waits until CLOSE_SESSION triggers Quit
```

`g_ui_host.GetFunc().IsNull()` 检查是一个链接拓扑探针：如果 AppHost 没有通过 `_SA_UIMain` 成功注入 fake host，插件会返回 99，而不是继续运行到空函数表崩溃。

## 链接拓扑要求

M4 的链接拓扑必须保持以下边界：

```text
demo_app.so
  -> depends on //third_party:gkc_plugin_runtime
     provides plugin-local GKC::g_ui_host and exported _SA_UIMain
  -> depends on //third_party:GkcSys

apphost_bin
  -> depends on src/apphost:plugin_loader
  -> depends on src/apphost:ui_host_impl
  -> must NOT depend on //third_party:gkc_plugin_runtime
```

原因：

```text
GKC::g_ui_host must be plugin-local.
```

如果 AppHost 自己也链接插件侧 `GkcGui.cpp`，AppHost 进程里会多出一份自己的 `GKC::g_ui_host`。插件 `.so` 里的 `GKC::g_ui_host` 仍然是另一份。AppHost 写自己的那份不会被插件看到，插件 wrapper 读取自己的那份仍然为空，最终会导致 `g_ui_host.GetFunc()` 为空或崩溃。

当前设计是：

```text
AppHost owns implementation:
  UiHostImpl + kHostTable

Plugin owns storage:
  plugin-local GKC::g_ui_host

_SA_UIMain performs injection:
  plugin-local g_ui_host = AppHost's LcInterface<IUiHost>
```

| `ConnectAndReady` | AppHost 子进程能连接 fake Gateway 并发送 `APPHOST_READY` |
| `HeartbeatEcho` | Gateway 发 `HEARTBEAT`，AppHost echo 返回 |
| `CloseSessionExits` | Gateway 发 `CLOSE_SESSION`，AppHost 自行退出 |
| `MultiPacketOrdering` | 多包发送顺序不乱 |

## 当前边界与留给 M5/M6 的内容

M4 已完成服务端插件加载和像素输出，但有明确边界：

| 边界 | 当前状态 | 后续 |
|------|----------|------|
| `INPUT_EVENT` | AppHost handler 已注册但直接忽略 | M5 通过 `PostWork` 注入 `DoMouse/DoKeyboard` |
| Plugin args | `PluginLoader::run()` 传 empty args | 后续需要时转发 app 参数 |
| `--width/--height` | CLI/Gateway 已传递，demo 插件未消费 | 后续可通过 args 或配置注入插件 |
| Timer | `AddTimer` 返回 0 | 有插件依赖 timer 时再实现 |
| Dialog/Popup | 返回 0，不支持 | 视业务需要扩展 |
| Client 显示 | 不属于 M4 | M6 实现真实 Client viewer |
