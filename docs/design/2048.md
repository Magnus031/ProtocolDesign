# 2048 App — Requirement and MVP Design

## One-line Summary

新增一个服务端 2048 AppHost 插件，让现有 Windows `client.exe + client_viewer.dll`
通过 Gateway 启动 `app_2048`，显示 4x4 棋盘、分数，并通过键盘方向键操作游戏。
本阶段不修改 wire protocol，只复用现有 `SPAWN_APP` / `PIXEL_DATA` /
`INPUT_EVENT` 链路。

## Product Goal

2048 的目标不是做一个完整商业游戏，而是作为 M6 之后的端到端应用示例，证明当前架构
已经可以承载一个有状态、可交互、持续重绘的远程 UI 应用：

- AppHost 维护真实业务状态。
- Client 只负责显示像素和转发输入。
- Gateway 仍然只做 session 路由，不理解 2048 业务。
- 用户可以在 Windows 上像操作本地窗口一样操作 Linux 侧运行的游戏。

## MVP Scope

### In Scope

| Area | Requirement |
|------|-------------|
| Board | 固定 4x4 棋盘。每个格子要显示当前 tile 数值；空格显示为空底色。 |
| Score | 界面顶部或侧边显示当前分数。每次 merge 后把合并出的 tile 数值加到 score。 |
| Input | `KEY_DOWN` 的 `KB_Left` / `KB_Right` / `KB_Up` / `KB_Down` 触发移动。 |
| Restart | `KEY_DOWN(KB_F2)` 重新开始游戏，清空分数并重新生成初始两个 tile。 |
| Rendering | 每次有效移动后重绘整张游戏界面。MVP 不要求动画。 |
| Merge Color | 每次发生 merge 的 tile 在本次重绘中使用强调色，下一次移动后恢复普通 tile 配色。 |
| Game Over | 无可移动方向时显示 `GAME OVER` 或等价的简单状态提示。 |
| App launch | Gateway allowlist 中新增 `app_2048`，Client 使用 `--app=app_2048` 启动。 |

### Out of Scope

- 不做动画、缓动、滑动过渡。
- 不做撤销、排行榜、存档。
- 不做鼠标操作。
- 不做文字输入协议扩展。
- 不引入新协议命令。
- 不要求复杂字体；MVP 可以使用内置 bitmap 数字/字母。
- 不要求 AppHost / Client 在本阶段迁移到 GKC IoPool。当前单连接 reader-thread 网络模型足以支撑 MVP。

## User Experience

### Window Layout

先明确两个尺寸概念：

- **Logical canvas**：AppHost 插件真实绘制、`PIXEL_DATA` 真实传输的像素尺寸。
- **Display scale**：Windows client_viewer 把 logical canvas 放大到屏幕上的倍数。

例如 `--canvas-width=160 --canvas-height=200 --display-scale=4` 表示：

- AppHost 发送的是 `160 x 200` 的像素画面。
- Client 窗口显示为 `640 x 800`。
- 网络上传输的数据量按 `160 x 200` 计算，不按 `640 x 800` 计算。

MVP 推荐使用一个比 `demo_app` 更大的固定逻辑画布：

```
logical canvas: 160 x 200
display scale : 4
visible window: 640 x 800
```

这个尺寸比当前 `demo_app` 的 `32 x 16` 明显更适合棋盘和分数板，同时每帧未压缩
像素量约为 `160 * 200 * 4 = 128 KB`，对当前单连接 MVP 仍然可接受。如果手动演示时
窗口偏小，可以只提高 `display-scale`，例如 `5` 会显示为 `800 x 1000`，不改变
AppHost 逻辑画布和网络数据量。

布局建议：

```
┌──────────────────────────────┐
│  2048          SCORE 000000  │  height ~24
├──────────────────────────────┤
│                              │
│    ┌────┬────┬────┬────┐    │
│    │    │ 2  │    │ 4  │    │
│    ├────┼────┼────┼────┤    │
│    │    │    │    │    │    │
│    ├────┼────┼────┼────┤    │
│    │ 8  │    │ 16 │    │    │
│    ├────┼────┼────┼────┤    │
│    │    │    │    │    │    │
│    └────┴────┴────┴────┘    │
│                              │
│  GAME OVER / PRESS F2        │  optional status line
└──────────────────────────────┘
```

The exact pixel-perfect layout is not important for MVP. What matters:

- Board is clearly 4x4.
- Score is always visible.
- Tile values are readable.
- Merge feedback is visible through a color change.
- F2 reset is visually reflected immediately.

### Color Rules

MVP can use a simple deterministic palette:

| Tile | Normal color | Merge highlight |
|------|--------------|-----------------|
| 2 / 4 | light colors | brighter yellow |
| 8 / 16 / 32 | medium warm colors | orange |
| 64+ | stronger colors | red or magenta accent |

Merge highlight rule:

- During a move, any destination tile produced by a merge is marked `merged_this_turn = true`.
- The next `DoDraw` paints marked tiles with highlight color.
- Before processing the next input, all merge flags are cleared.

This is intentionally simple. It provides visible feedback without needing animation.

## Game Rules

Use standard 2048 rules:

1. Game starts with two random tiles.
2. New tiles are normally `2`, occasionally `4`.
3. A move compresses all tiles toward the selected direction.
4. Adjacent equal tiles merge once per move.
5. The score increases by the value of each merged tile.
6. If the board changed, spawn one new tile.
7. If no empty cells remain and no adjacent equal tiles exist, enter game-over state.
8. `F2` restarts regardless of current state.

Randomness:

- MVP can use a deterministic `std::mt19937` seed in tests.
- Runtime can seed from time or process entropy.
- Tests should avoid depending on exact random positions unless a deterministic seed is injected.

## Architecture Fit

### Component Responsibilities

| Component | Responsibility |
|-----------|----------------|
| `plugins/app_2048` | Own board state, score, random tile generation, input handling, drawing. |
| `src/apphost` | Load the plugin, inject fake `IUiHost`, convert plugin draws to `PIXEL_DATA`. |
| `src/gateway` | Spawn AppHost through allowlist, route packets by session. No 2048 logic. |
| `src/client` | Connect to Gateway, apply `PIXEL_DATA`, forward keyboard input. No 2048 logic. |
| `plugins/client_viewer` | Display the pixel backstore and forward keyboard events. Should remain app-agnostic. |

### Protocol

No protocol change is required.

Input path:

```
Windows key press
  -> client_viewer DoKeyboard
  -> INPUT_EVENT(KEY_DOWN, keyCode)
  -> Gateway route
  -> AppHost
  -> app_2048 DoKeyboard
  -> update board
  -> Damage(full window)
  -> PIXEL_DATA
```

Pixel path:

```
app_2048 DoDraw
  -> AppHost fake IUiHost captures pixels
  -> PIXEL_DATA dirty rect
  -> Gateway route
  -> ClientRuntime apply_pixel_data_body
  -> client_viewer repaint
```

### Canvas Size Constraint

Current M6a implementation has an important limitation: there is no window-size negotiation in
the protocol. The Client `PixelRenderer` must be initialized with a logical canvas large enough
to accept the rects emitted by AppHost.

For 2048 MVP, use one of these approaches:

1. **Recommended**: parameterize `client_viewer` with canvas/display size arguments, for example:

   ```
   --canvas-width=160 --canvas-height=200 --display-scale=4
   ```

   Then run:

   ```
   client.exe ^
     --plugin=.\client_viewer.dll ^
     --gateway-host=<gateway-ip> ^
     --gateway-port=19000 ^
     --app=app_2048 ^
     --canvas-width=160 ^
     --canvas-height=200 ^
     --display-scale=4
   ```

2. **Fallback**: create a dedicated `client_2048_viewer.dll` with fixed 160x200 logical canvas.

Do not add implicit resizing to `PixelRenderer` based only on incoming `PIXEL_DATA` in MVP unless
the resize semantics are explicitly designed. Silent resize on arbitrary packets can hide protocol
or routing bugs.

## MVP Implementation Plan

### Step 1 — Pure Game Logic

Implement board logic first, independent of GKC:

```cpp
struct MoveResult {
    bool changed;
    bool merged;
    uint32_t score_delta;
};
```

Required test cases:

- Move left with no merge.
- Move left with one merge.
- A tile cannot merge twice in one move.
- Score increases by merged tile values.
- No new tile is spawned when the board does not change.
- Game-over detection works.
- F2/reset creates a clean board with score 0.

### Step 2 — AppHost Plugin Rendering

Add `plugins/app_2048` as a GKC plugin:

- `GuiMain` creates one `ToplevelImpl<App2048Window>`.
- `Create(true, 160, 200)`.
- `Show(true)`.
- `DoDraw` paints full UI into `pDraw->pBuffer`.
- `DoKeyboard` handles arrows and F2.
- On valid state change, call `Damage(full window)`.

Rendering can use direct pixel drawing helpers:

- `fill_rect`
- `draw_border`
- `draw_digit_bitmap`
- `draw_number`
- `draw_text_small`

### Step 3 — Client Viewer Size Support

If using the recommended path, update `client_viewer` to parse:

- `--canvas-width=<n>`
- `--canvas-height=<n>`
- `--display-scale=<n>`

Then initialize:

- `PixelRenderer(canvas_width, canvas_height)`
- window size = `canvas_width * display_scale` by `canvas_height * display_scale`
- mouse coordinate scaling based on parsed dimensions

This keeps the viewer generic and reusable for future apps.

### Step 4 — Gateway/AppHost Manual Launch

Linux side example:

```bash
bazel build //src/gateway:gateway_bin //src/apphost:apphost_bin //plugins/app_2048:app_2048

bazel-bin/src/gateway/gateway_bin \
  --public-port=19000 \
  --apphost-internal-port=19001 \
  --apphost-bin=bazel-bin/src/apphost/apphost_bin \
  --app=app_2048=bazel-bin/plugins/app_2048/libapp_2048.so
```

Windows side example:

```powershell
.\client.exe ^
  --plugin=.\client_viewer.dll ^
  --gateway-host=<gateway-ip> ^
  --gateway-port=19000 ^
  --app=app_2048 ^
  --canvas-width=160 ^
  --canvas-height=200 ^
  --display-scale=4
```

## Acceptance Criteria

### Automated

- `app_2048_logic_test` passes on Linux.
- Existing Gateway/AppHost tests still pass on Linux.
- Existing Client tests still pass on Windows for client-side changes.
- If `client_viewer` is parameterized, add or update focused tests where feasible for option parsing or renderer sizing.

### Manual End-to-End

On Linux Gateway/AppHost + Windows Client:

1. Client starts `app_2048`.
2. Window displays a 4x4 board and score area.
3. Arrow keys move tiles.
4. Merge increases score.
5. Merged tile visibly changes color for that turn.
6. `F2` restarts the board and resets score.
7. Game-over state is visible when no moves remain.
8. The session runs for at least 60 seconds without crash or stuck UI.

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Client/AppHost canvas size mismatch | Client rejects `PIXEL_DATA` as `BAD_RECT` | Parameterize client viewer and document matching launch args. |
| Text rendering becomes too complex | Delays MVP | Use built-in bitmap digits and minimal block letters. |
| Random tile placement makes tests flaky | Unstable tests | Isolate pure logic and inject deterministic RNG seed. |
| Full-frame redraw is inefficient | Higher bandwidth | Accept for MVP; 160x200x4 is still small enough for turn-based 2048. Optimize dirty rects later. |
| Blocking socket send stalls under bad network | UI responsiveness risk | Accept for MVP single-session use; consider IoPool migration later. |

## Open Questions

1. Is `160x200` logical canvas large enough for the manual demo, or should MVP use `192x240`?
2. Should runtime random seed be deterministic during manual demos for repeatability?
3. Should `F2` reset be the only restart path, or should game-over also accept any arrow key to restart?

## PM Recommendation

Use this MVP path:

1. Build and test pure `app_2048_logic`.
2. Parameterize `client_viewer` canvas/display size so it is reusable across apps.
3. Implement `plugins/app_2048` with fixed `160x200` logical canvas.
4. Run end-to-end through the existing Gateway/AppHost/Client chain.

This keeps 2048 focused on proving the architecture, while avoiding unnecessary protocol changes
or UI polish work before the game loop is reliable.
