# M5 — INPUT_EVENT closed loop + PostWork main-thread model

## One-line summary

M5 closes the reverse direction of the M4 link.  The Client (in M5: a fake
test socket) sends `INPUT_EVENT` packets that the Gateway routes by SessionID
without inspecting their bodies.  AppHost parses the body on its network
reader thread, copies the event into an owns-data queue inside `UiHostImpl`,
and uses `PostWork` to defer dispatch to the plugin main thread.  The plugin
runs `DoMouse` / `DoKeyboard` on that main thread and may call `Damage()`,
which re-enters the M4 `dispatch_draw_and_send()` path and produces a fresh
`PIXEL_DATA` packet.

Where M4 proved that **the plugin can drive output frames**, M5 proves that
**remote input can drive plugin state changes safely across threads.**  No
new protocol command was added — `INPUT_EVENT (0x20)` was already reserved
in M1.  The new pieces are body layout, helper code, queue/dispatch in
`UiHostImpl`, and demo behaviour in `demo_app`.

## Body layouts (as implemented)

`CmdType::INPUT_EVENT (0x20)`.  Header.session_id selects the AppHost; the
Gateway never reads the body.

```
Mouse (13 bytes, eventType in 0x01..0x06):
[eventType:1][x:BE32][y:BE32][timestamp:BE64]
  0x01 MOUSE_MOVE
  0x02 MOUSE_LEFT_DOWN
  0x03 MOUSE_LEFT_UP
  0x04 MOUSE_RIGHT_DOWN
  0x05 MOUSE_RIGHT_UP
  0x06 MOUSE_SCROLL

Keyboard (11 bytes, eventType in 0x10..0x11):
[eventType:1][keyCode:BE16][timestamp:BE64]
  0x10 KEY_DOWN
  0x11 KEY_UP
```

`keyCode` carries GKC `UiMessageKeyboard::btKey` values (`KB_F1`, `KB_Left`,
…).  Even though the wire field is BE16, the parser rejects any value
greater than `0xFF`: `btKey` is one byte and we do not silently truncate.
Timestamps are Client-side microseconds; the M5 demo does not consume them
but the parser preserves them in `ParsedInputEvent::timestamp_us` for
future telemetry.

### Reject policy

`parse_input_event_body()` returns `false` (and the AppHost reader silently
drops the packet) for any of:

| Cause            | Example                                |
|------------------|----------------------------------------|
| Empty body       | `body_length == 0`                     |
| Unknown eventType| `0x00`, `0x07`, `0x12`, `0xFF`, …      |
| Wrong length     | mouse body sized 12 or 14, etc.        |
| `keyCode > 0xFF` | KEY_DOWN with `keyCode == 0x0100`      |

A bad packet must never tear down the session: `INPUT_EVENT` is data plane,
and the M3 `ERROR_RESP` path is reserved for control-plane mismatches.

## Threading boundary

```
network reader thread                    plugin main thread
─────────────────────                    ──────────────────
recv() raw bytes
  └─ MessageHandler.feed()
       └─ INPUT_EVENT lambda
            ├─ parse_input_event_body() → ParsedInputEvent
            └─ ui_host_.post_*_input(msg)
                 ├─ lock(state_->mtx)
                 ├─ input_queue.push_back(copy)
                 ├─ if !input_work_pending:
                 │    input_work_pending = true
                 │    schedule = true
                 └─ unlock
                 if schedule:
                   on_host_post_work(this, drain_input_work_static, this)
                                            (cv.notify_all wakes Loop)
                                                  ────►
                                                  on_host_loop() drains post_queue
                                                    └─ drain_input_work_static(self)
                                                        └─ drain_input_queue_on_main_thread()
                                                             ├─ swap queue under lock,
                                                             │   then release lock
                                                             ├─ for each ev:
                                                             │    dispatch_mouse / dispatch_keyboard
                                                             │      └─ window.handler.Process(
                                                             │             UI_MESSAGE_MOUSE/KEYBOARD)
                                                             │           └─ DemoWindow::DoMouse/DoKeyboard
                                                             │               └─ Damage(rect)
                                                             │                 → dispatch_draw_and_send()
                                                             │                   → DoDraw
                                                             │                   → pack_pixel_data_rect
                                                             │                   → sink → send_pixel_data()
                                                             │                       (writes to socket;
                                                             │                        send_mtx_ serialises)
                                                             └─ end loop
```

Two invariants make this safe:

1. **Plugin handler is only invoked on the main thread.**  The reader thread
   never calls `window.handler.Process` directly; it only mutates the
   `input_queue` under `state_->mtx`.  `dispatch_mouse` and
   `dispatch_keyboard` are private members called only from
   `drain_input_queue_on_main_thread()`.
2. **No host mutex held while plugin code runs.**  The drain function
   `swap()`s the queue into a local container before releasing the lock,
   so any synchronous `Damage()` → `DoDraw()` → `PIXEL_DATA` chain runs
   without contending against an enqueueing reader thread.

## Coalesced PostWork

A naïve design would post one `WorkProc` per input event, growing
`post_queue` linearly with input rate.  `UiHostImpl` instead uses a single
boolean (`State::input_work_pending`):

```
post_*_input():
  lock
  push event into input_queue
  if not input_work_pending:
      input_work_pending = true
      schedule = true
  unlock
  if schedule: PostWork(drain_input_work_static)
```

```
drain_input_queue_on_main_thread():
  lock
  swap input_queue -> local
  input_work_pending = false
  unlock
  for each ev in local: dispatch...
```

A burst of N events therefore enqueues at most one drain `WorkProc`.  Once
`drain` runs, the next `post_*_input` call after that drain enqueues a
fresh `WorkProc`.  `m5_input_test` `PostWorkThreadSafety` exercises this
with 100 fast `LEFT_DOWN` events; the assertion is that AppHost stays
responsive and exits cleanly on `CLOSE_SESSION`, not that 100 frames are
emitted.

## Demo plugin behaviour

`plugins/demo_app/demo_app.cpp` keeps the M4 32×16 window and the
`{8,4,16,12}` small rect.  Its `DoDraw` discriminates by call count:

| `draw_count_` | Trigger              | Background | Small rect |
|---------------|----------------------|------------|------------|
| 1             | `Show(true)`         | BLUE       | RED        |
| 2             | initial `Damage(small)` | BLUE    | GREEN      |
| ≥ 3           | input-driven `Damage()` | `bg_color_` (latched) | `small_color_` (latched) |

State machine for input:

```
DoMouse:
  if uEvent == MOUSE_EVENT_DOWN
     and btButton == MOUSE_BUTTON_LEFT
     and (x, y) inside small rect:
        small_color_ = (small_color_ == GREEN) ? YELLOW : GREEN
        Damage(small_rect)

DoKeyboard:
  if btDown == 1 and btKey == KB_F1 (0x70):
        bg_color_ = (bg_color_ == BLUE) ? CYAN : BLUE
        Damage(full_window)
```

Other inputs (mouse moves, mouse clicks outside the small rect, every key
besides `KB_F1`, keyboard up events, scroll) are silently ignored — no
`Damage()` call, no new frame.  This gives the test the
`NoInputNoPixelData` and `MouseOutsideTargetNoFrame` properties for free.

The M4 startup frames are preserved verbatim, so M4 regression tests
(`m4_plugin_test`, `gateway_m4_plugin_test`) keep passing without any
modification.

## Test coverage

### `input_event_test` (unit)

- Pack lengths: mouse body == 13, keyboard body == 11
- Reject: empty body, unknown eventType, mouse wrong length, keyboard
  wrong length, `keyCode > 0xFF`
- Field mapping: `KEY_DOWN(KB_F1)` → `btDown=1`, `btKey=0x70`;
  `KEY_UP(KB_Left)` → `btDown=0`; `LEFT_DOWN` → `MOUSE_EVENT_DOWN`
  + `MOUSE_BUTTON_LEFT` + `MOUSE_STATE_LEFT`; `MOUSE_MOVE` → button NONE;
  `SCROLL` → `MOUSE_EVENT_WHEEL`

### `m5_input_test` (AppHost local integration)

| Test | Asserts |
|------|---------|
| `MouseClickChangesPixel`     | `LEFT_DOWN` at `(12, 8)` produces a small-rect dirty `PIXEL_DATA` whose pixels are all YELLOW; `frameSeq` increments past startup |
| `KeyboardEventRouted`        | `KEY_DOWN(KB_F1)` produces a full-window `PIXEL_DATA` with CYAN background and GREEN small rect |
| `NoInputNoPixelData`         | After draining startup, a 1s recv timeout expires with no extra `PIXEL_DATA` |
| `InvalidInputIgnored`        | Empty body, unknown eventType, wrong-length mouse, `keyCode=0x100` keyboard — no frames, AppHost still alive (a follow-up valid `KB_F1` does produce a frame) |

### `gateway_m5_input_test` (Gateway coupled)

`GatewayRoutesInputEventToAppHostAndPixelsBack`: real Gateway with
`auto_spawn_apphost=true`, fake Client `SPAWN_APP("demo_app")` →
`SESSION_ACK` → drain two startup PIXEL_DATA → send `INPUT_EVENT(KEY_DOWN,
KB_F1)` → expect a CYAN-background full-window `PIXEL_DATA` carrying the
real `session_id`.  This proves Gateway forwards the body verbatim and the
public/internal port binding survives.

## What M5 deliberately did not change

- **Gateway business logic.**  No body parsing for `INPUT_EVENT`; routing
  remains by `Header.session_id` only.
- **No timer / wheel-delta / DPI.**  Wheel maps to `MOUSE_EVENT_WHEEL` with
  `btValue=0`; protocol has no delta field yet.  Coordinate scaling is the
  Client's responsibility (M6).
- **No `INPUT_EVENT` ACK.**  Input is lossy data plane; if the link drops
  the session is torn down by `CLOSE_SESSION` / heartbeat timeout, not by
  application-level acks.
