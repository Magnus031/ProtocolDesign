# M3 — Gateway 路由与 AppHost 生命周期管理

## 一句话总结

M3 将 Gateway 从“单纯的 TCP 监听器”推进为系统的运行时控制面：它负责接入 Client、接入 AppHost、分配 SessionID、维护双向路由、按需 fork/exec AppHost 进程，并用心跳与超时机制清理异常 session。

---

## 在整个项目中的位置

```
M1 (协议层) ✅ → M2 (IoPool+MessageHandler) ✅
                         ↓
                 M3a (Gateway 路由) ✅
                         ↓
                 M3b (进程管理) ✅ ← 当前完成
                         ↓
                 M4 (真实 UIHost / 插件绘制) → M5 → M6
```

M3 是**控制面 milestone**。M2 已经证明了单组件如何用 IoPool 收发协议包；M3 则把这些连接组织成“一个 Client session 对应一个 AppHost runtime”的完整运行模型。

## 设计哲学

### 1. Gateway 是控制面，不解析业务语义

Gateway 只理解协议头、SessionID 和少量控制指令：

- `SPAWN_APP`：创建 session / 启动 AppHost
- `APPHOST_READY`：绑定 AppHost 连接
- `HEARTBEAT`：保持活性
- `CLOSE_SESSION`：关闭会话
- 其他业务包：按 SessionID 原样转发

例如 `INPUT_EVENT` 和 `PIXEL_DATA` 的 body 对 Gateway 是透明的。这样 Gateway 不被 UI、插件、像素格式、输入格式耦合，后续 M4/M5/M6 可以继续演进业务 payload，而 Gateway 的路由核心保持稳定。

### 2. Session 是系统的最小运行时单元

一个 session 不是简单的 socket 映射，而是完整运行时状态：

```
SessionRuntime
├── session_id
├── state: SPAWNING / ACTIVE / CLOSING / DEAD
├── client_conn       Client 侧 IoPool handle
├── apphost_conn      AppHost 侧 IoPool handle
├── apphost_pid       fork/exec 出来的 OS 子进程 pid
├── app_name          Client 请求的逻辑应用名
├── plugin_path       allowlist 映射后的本地插件路径
├── spawn_deadline    启动握手超时点
├── last_client_seen  Client 最近一次有效包时间
└── last_apphost_seen AppHost 最近一次有效包时间
```

因此 M3 的范式是：**所有 Gateway 决策都回到 SessionTable**。路由、进程、心跳、超时不分散在多个互不知情的 map 里，避免状态漂移。

### 3. 连接是事件驱动的，spawn 不是同步建连

`fork/exec` 只能创建进程，不能自动得到 Gateway 与 AppHost 的 TCP 连接。因此 auto-spawn 是两阶段流程：

```
Client -> Gateway: SPAWN_APP(app_name)
Gateway:
  1. 校验 app_name 和 allowlist
  2. 创建 SPAWNING session
  3. fork/exec AppHost，并传入 session_id / gateway host / gateway port
  4. 记录 apphost_pid

AppHost -> Gateway internal port:
  5. AppHost 启动后主动 connect Gateway
  6. AppHost 发送 APPHOST_READY(session_id)

Gateway:
  7. bind_apphost(session_id, apphost_conn)，状态变 ACTIVE
  8. 发送 SESSION_ACK 给 Client
```

这就是为什么 `handle_spawn_app()` 里不会立即回复 `SESSION_ACK`。只有收到 `APPHOST_READY`，Gateway 才知道“哪个 AppHost socket 属于哪个 session”，后续才能安全路由 `INPUT_EVENT` 和 `PIXEL_DATA`。

## 核心架构设计

### 1. 双端口 Gateway

Gateway 同时监听两个 TCP 端口：

| 端口 | 用途 |
|------|------|
| `public_port` | Client 连接入口 |
| `apphost_internal_port` | AppHost 反向连接入口 |

对应代码路径：

```
Gateway::start(config)
  ├── StartListen(public_port, on_client_listen_event)
  ├── StartListen(apphost_internal_port, on_apphost_listen_event)
  └── 启动 monitor_thread
```

Client 连接到 public port 后分配 `ClientSession`；AppHost 连接到 internal port 后分配 `AppHostSession`。两类连接都复用 M2 建立的 per-connection context + send queue + generation 防复用模式。

### 2. Client-side 收包路径

```
Client TCP data
  -> ClientSession::on_client_event(IO_TYPE_RECEIVED)
  -> Gateway::Impl::on_client_received()
  -> MessageParser.next_packet()
  -> mark_client_seen()
  -> switch CmdType
       SPAWN_APP      -> handle_spawn_app()
       HEARTBEAT      -> echo HEARTBEAT
       CLOSE_SESSION  -> close_session()
       default        -> forward_to_apphost()
```

`mark_client_seen()` 在进入 `switch` 前执行，因此不只有 HEARTBEAT 会刷新活性时间；任何合法 Client 包都会刷新 `last_client_seen`。

### 3. AppHost-side 收包路径

```
AppHost TCP data
  -> AppHostSession::on_apphost_event(IO_TYPE_RECEIVED)
  -> Gateway::Impl::on_apphost_received()
  -> MessageParser.next_packet()
  -> mark_apphost_seen()
  -> switch CmdType
       APPHOST_READY  -> handle_apphost_ready()
       HEARTBEAT      -> echo HEARTBEAT
       CLOSE_SESSION  -> close_session()
       default        -> forward_to_client()
```

同理，AppHost 发送 `APPHOST_READY`、`HEARTBEAT`、`PIXEL_DATA` 等任何合法包，都会刷新 `last_apphost_seen`。

### 4. SessionTable 索引设计

SessionTable 维护一个主表和三个反向索引：

```
by_session_: session_id -> SessionRuntime
by_client_:  client_conn -> session_id
by_apphost_: apphost_conn -> session_id
by_pid_:     apphost_pid -> session_id
```

这些索引分别服务于不同事件来源：

| 事件来源 | 需要的反查 |
|----------|------------|
| Client 发包 / 断开 | client_conn -> session_id |
| AppHost 发包 / 断开 | apphost_conn -> session_id |
| `waitpid()` 发现子进程退出 | apphost_pid -> session_id |
| 协议转发 | session_id -> client_conn / apphost_conn |

`transition_to_closing()` 是清理路径的关键：它把 session 原子地标记为 `CLOSING`，并复制出 route/pid。这样 AppHost crash、socket close、heartbeat timeout 几条路径同时触发时，只有第一条会真正执行清理。

## AppHost 进程生命周期

### 1. spawn_apphost()

`ProcessManager::spawn_apphost()` 做的是 Linux 进程层面的启动：

```
Gateway parent
  -> fork()
      parent: 得到 child pid，返回 true
      child:  execv(apphost_bin, argv)
```

传给 AppHost 的 argv 包括：

```
--session-id=<session_id>
--gateway-host=<host>
--gateway-port=<port>
--plugin=<plugin_path>
--width=<width>
--height=<height>
```

注意：`spawn_apphost()` 返回 `true` 只代表 `fork()` 成功，不代表 `execv()` 成功，也不代表 AppHost 已 ready。真正的 ready 信号是后续 TCP 连接上的 `APPHOST_READY`。

### 2. AppHost 反向连接

`src/apphost/main.cpp` 中，当 AppHost 检测到 `--gateway-host` 参数时进入 gateway-client mode：

```
run_gateway_client_mode()
  ├── 解析 --gateway-host / --gateway-port / --session-id
  ├── connect_to_gateway(host, port)
  ├── send APPHOST_READY(session_id)
  └── 等待 Gateway 的 HEARTBEAT / CLOSE_SESSION
```

这是 M3b 的最小 AppHost 生命周期闭环：Gateway 可以启动进程，AppHost 可以注册自己，Gateway 可以在 session 关闭时通知或终止它。

### 3. reap_exited()

`ProcessManager::reap_exited()` 使用：

```cpp
waitpid(-1, &status, WNOHANG)
```

含义：

- `-1`：检查 Gateway 拥有的任意子进程
- `status`：接收退出码或信号信息
- `WNOHANG`：非阻塞；没有子进程退出时立即返回

函数用循环一次性收割所有已退出 AppHost，避免 zombie 进程堆积。Gateway monitor thread 再通过 `by_pid_` 找回 session，并进入失败清理。

## Monitor Loop：为什么既要 waitpid 又要 timeout

`monitor_loop()` 每隔 `monitor_interval_ms` 做两类检查：

### 1. OS 已确认 AppHost 退出

```
process_manager_.reap_exited()
  -> sessions_.find_by_pid(exited.pid)
  -> fail_session(session_id, true)
```

覆盖 case：

- AppHost crash
- AppHost main 返回
- `execv()` 后程序很快退出
- AppHost 被外部 kill

这是进程层面的硬事实，由 OS 提供。

### 2. Session 层面超时

`waitpid()` 只能发现“进程死了”，不能发现“进程还活着但协议不可用”。因此 monitor 还会扫描 `sessions_.snapshot_sessions()`：

| 状态 | 条件 | 说明 | 处理 |
|------|------|------|------|
| `SPAWNING` | `now > spawn_deadline` | AppHost 可能还活着，但没有及时反连并发送 `APPHOST_READY` | `fail_session(id, true)` |
| `ACTIVE` | `now - last_client_seen > client_timeout_ms` | Client 长时间没有任何有效包，视为客户端不可用 | `fail_session(id, false)` |
| `ACTIVE` | `now - last_apphost_seen > apphost_timeout_ms` | AppHost 进程/socket 可能存在，但协议层无响应 | `fail_session(id, true)` |

`notify_client_error` 的含义：

- `true`：后端失败或启动失败，需要给 Client 发 `ERROR_RESP`
- `false`：Client 自己已经超时，不再尝试通知它

## 安全边界与配置范式

### 1. Client 只能请求逻辑 app name

`SPAWN_APP` body 中携带的是 `appName`，不是本地文件路径。Gateway 先校验 app name：

- 非空，长度不超过 255
- 不包含 `..`
- 不包含 `/` 或 `\`
- 只允许字母、数字、`_`、`-`、`.`

然后通过本地 allowlist 映射到真实插件路径：

```
demo_app -> ./plugins/demo_app/libdemo_app.so
```

这样 Client 不能通过协议请求任意本地 `.so` 文件。

### 2. execv 不经过 shell

AppHost 启动使用 `execv()`，不是 `system()`。因此 `plugin_path` 和其他参数不会被 shell 展开或解释，降低命令注入风险。

### 3. Gateway CLI

```
gateway \
  --public-port 19000 \
  --apphost-internal-port 19001 \
  --apphost-bin ./bazel-bin/src/apphost/apphost_bin \
  --app=demo_app=./plugins/demo_app/libdemo_app.so
```

只要提供 `--apphost-bin`，Gateway 就进入 auto-spawn 模式，并要求至少提供一个 `--app=name=plugin_path` allowlist 项。

## 本轮形成的开发范式

| 范式 | 说明 |
|------|------|
| 控制面与数据面分离 | Gateway 管 SessionID 和连接路由，不解析 `INPUT_EVENT` / `PIXEL_DATA` body |
| 先注册 runtime，再等待 ready | `SPAWN_APP` 只创建 `SPAWNING` session；`APPHOST_READY` 才完成 ACTIVE 绑定 |
| 进程状态和协议状态都要监控 | `waitpid()` 发现进程退出；snapshot timeout 发现启动卡住、心跳停止、半开连接 |
| 所有清理入口汇聚到 fail/close path | crash、timeout、disconnect、close packet 都最终回到 SessionTable 状态转换和统一资源释放 |
| SessionTable 是唯一事实源 | route、pid、last_seen、state 集中维护，避免 Gateway 内部多个状态表互相漂移 |
| allowlist 而非任意路径 | Client 请求逻辑 app name，Gateway 本地解析到插件路径，保持部署控制权 |

M3 完成后，系统已经具备“Client 请求一个远程应用，Gateway 创建后端 AppHost，建立双向路由，并在异常时回收资源”的基础运行时骨架。后续 M4 可以在这个骨架上把 AppHost 从最小 gateway-client mode 推进到真实插件加载、GKC UIHost 绘制和脏矩形像素回传。
