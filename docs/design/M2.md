# M2 — IoPool + MessageHandler 基础设施

## 一句话总结

建立所有三个组件（AppHost / Gateway / Client）共用的网络 I/O 骨架：per-connection 上下文管理模式 + CmdType 消息分发器。AppHost 作为第一个使用者，在指定端口监听，收到 SPAWN_APP 后回复静态 PIXEL_DATA 帧。

---

## 在整个项目中的位置

```
M1 (协议层) ✅ → M2 (IoPool+MessageHandler) ← 当前
                      ↓
              M3a (Gateway 路由) → M3b (进程管理) → M4 → M5 → M6
```

M2 是**网络基础设施 milestone**：它提供了 IoPool 连接管理和消息分发的通用模式，后续 Gateway（M3a）和 Client（M6）都复用这套模式。

## 核心架构设计

### 1. Per-connection 上下文（ConnContext 模式）

每个 TCP 连接对应一个 `ConnContext`，生命周期由 `free_list<ConnContext>` + 原子自旋锁管理，**全程无 `new`/`delete`**：

```
ConnContext : public node_base
├── id_            IoPool 连接句柄（BeginInput/DisableHandle 需要）
├── generation_    free_list 槽位复用代数（延后 drain 时防止误操作新连接）
├── next_active_   侵入式活跃链表指针（shutdown 时遍历清理）
├── io_func_       嵌入式 _IoFunc（Exec = on_io_event），SetHandleFunc 时绑定
├── handler_       MessageHandler（每连接独立 parser + CmdType 分发）
├── send_queue_    发送溢出队列（BeginInput 忙时按序暂存待发 buffer）
└── server_        反向指针 → AppHost::Impl
```

**分配协议（严格遵守）：**
```
FetchFreeNode(conn)   // 查看空闲链表头，不摘除
call_constructor(*conn) // 就地构造（构造失败则节点不丢失）
PickFreeNode()        // 构造成功后才摘除
```

### 2. MessageHandler — 可复用的分发层

```
┌─────────────────────────────────────────────┐
│ MessageHandler                               │
│                                              │
│  register_handler(HEARTBEAT, fn1)            │
│  register_handler(PIXEL_DATA, fn2)           │
│  register_handler(CLOSE_SESSION, fn3)        │
│                    ↓                         │
│  feed(raw_bytes)                             │
│       │                                      │
│       ▼                                      │
│  MessageParser.feed() → next_packet() 循环    │
│       │                                      │
│       ▼                                      │
│  handlers_[cmd_type](packet)  // 路由到对应fn │
└─────────────────────────────────────────────┘
```

- 内部持有 `MessageParser`（每连接独立状态）
- 未注册的 CmdType 静默丢弃
- `reset()` 丢弃半包状态，用于连接复用或 POISONED 恢复
- AppHost 已接入；Gateway 和 Client 后续直接复用，无需各自重写 CmdType 分发层

### 3. AppHost 数据流

```
main()
  ├── parse_port(argv) → port (默认 19001)
  └── server.start(port)
        └── _IoPool_Fetch() → StartListen(port, on_listen_event)

┌─ TCP 连接到达 ─────────────────────────────────────────┐
│                                                        │
│  IO_TYPE_ACCEPT_INIT                                   │
│    ├── alloc_conn() 取 ConnContext                      │
│    ├── register_handler(SPAWN_APP / HEARTBEAT / CLOSE)  │
│    ├── SetHandleFunc(conn_id, conn->io_func_, conn)     │
│    └── 此后所有事件直接回调 conn->on_io_event()          │
│                                                        │
│  IO_TYPE_RECEIVED                                      │
│    └── handler_.feed(data, len)                         │
│          ├── SPAWN_APP      → send_pixel_data()         │
│          │     └── capture_rect(buf, 0,0,w,h) 提取像素  │
│          ├── HEARTBEAT      → send_heartbeat()          │
│          └── CLOSE_SESSION  → DisableHandle(conn_id)    │
│                                                        │
│  send_pixel_data / send_heartbeat                       │
│    └── enqueue_send() → BeginInput/EndInput 或入队       │
│                                                        │
│  IO_TYPE_SENT                                          │
│    └── on_sent() 安排延后 drain_send_queue()            │
│          └── 回调返回后再 BeginInput/EndInput 下一项     │
│                                                        │
│  IO_TYPE_BEFORE_CLOSE                                  │
│    └── release_conn() → 归还 free_list                  │
└────────────────────────────────────────────────────────┘
```

### 4. PIXEL_DATA Body 格式

```
[frameSeq:4] [rectLeft:4] [rectTop:4] [rectRight:4] [rectBottom:4] [dataLen:4] [pixels:dataLen]
```

- 当前 M2 阶段发送固定 16×16 纯红色帧，通过 `capture_rect()` 从 PixelBuffer 提取像素后打包
- 像素字节序为 ARGB：[A, R, G, B]，与协议文档中的 `0xAARRGGBB` 大端约定一致
- `pixel_capture.h` 在 M4 将继续用于从 GKC `pDraw->pBuffer` 按 `rcPaint` 坐标裁出脏矩形

## 关键设计约束（M2 建立，全局遵守）

| 约束 | 说明 |
|------|------|
| IoPool 单例 | `_IoPool_Fetch()` / `_IoPool_Disable()` 进程全局唯一，同一进程只能启动一个 AppHost |
| 无 new/delete | Per-connection 上下文用 `free_list<T>` + 自旋锁，不在数据路径做堆分配 |
| 无 DirtyRectDetector | 脏矩形由 GKC `pDraw->rcPaint` 直接提供，本项目不做逐帧像素比对 |
| 无 src/network/ | 网络 I/O 全部经 GKC IoPool，不设独立网络模块 |
| per-connection MessageHandler | 每个连接独立持有 MessageHandler，内部 parser 状态不共享 |

## 测试覆盖

### 单元测试：`message_handler_test`（6 个用例）

| 用例 | 验证点 |
|------|--------|
| `DispatchToRegisteredHandlers` | 两个 CmdType 各注册 handler，分别被正确调用，session_id 传递正确 |
| `UnknownCmdTypeIgnored` | 未注册的 CmdType 静默丢弃，不崩溃 |
| `ByteByByteFeed` | 逐字节喂入（极端 TCP 分片），完整包仍然被正确解析和分发 |
| `TwoPacketsInOneFeed` | 一次 feed 包含两个完整包，两个都被分发 |
| `ResetClearsPartialState` | 喂入半个包头后 reset，后续完整包不受污染 |
| `RegisterOverwritesPreviousHandler` | 同一 CmdType 注册两次，旧 handler 被替换 |

### 集成测试：`apphost_test`（1 个函数，4 个场景）

| 场景 | 验证点 |
|------|--------|
| Scenario 1 — SPAWN_APP → PIXEL_DATA | 连接、发 SPAWN_APP、收到 PIXEL_DATA、rect=16×16、dataLen=1024、首像素纯红 |
| Scenario 2 — HEARTBEAT 往返 | 连接、发 HEARTBEAT、收到 HEARTBEAT 回复、session_id 一致、body_length=0 |
| Scenario 3 — CLOSE_SESSION | 连接、发 CLOSE_SESSION、等待 100ms、recv() 返回 ≤0 确认服务端已断开 |
| Scenario 4 — Two packets in one TCP write | 一次写入 SPAWN_APP+HEARTBEAT，使用持久 MessageParser 验证两个响应按序返回，并覆盖发送队列路径 |

## 本轮修复记录

| 问题 | 根因 | 处理 |
|------|------|------|
| `send_queue_` 第二项无法发出 | GKC 在 `IO_TYPE_SENT` 回调返回之后才清除 `iSend`，回调内立即 `BeginInput()` 会继续返回 null | `on_sent()` 只安排延后任务；延后任务在回调返回后调用 `drain_send_queue()`，一次只发送队列头部一项 |
| 延后 drain 可能遇到 ConnContext 释放/复用 | `free_list` 槽位地址可能被后续连接复用，延后任务只持有裸指针不够区分连接世代 | `ConnContext::generation_` 随分配递增，延后任务同时校验指针和 generation；`stop()` 等待 drain worker 退出 |
| `apphost_test` 连续读包可能丢第二包 | 原 `recv_one_packet()` 每次新建 parser；一次 `recv()` 收到多个完整响应时，函数返回第一个包并丢弃剩余字节 | 测试客户端改为 `BlockingTestClient`，每个 socket 持有一个持久 `MessageParser`，多次 `recv_one_packet()` 共享解析状态 |

> `MessageHandler` 已在 AppHost 的 per-connection 上下文中使用；`--port` 参数解析、`pixel_capture` 工具函数、CLOSE_SESSION 测试覆盖、动态测试端口、连续包发送队列测试均已实现。
